# 风险管理计划

## 1. 风险管理目标

风险管理计划用于识别、跟踪和控制项目实施过程中的范围、进度、技术、联调、质量和验收风险，确保项目能够在 45 个自然日内完成预验收和正式验收。

项目风险管理遵循提前识别、分级处理、持续跟踪、闭环验证的原则。

## 2. 风险分级

| 风险等级 | 判定标准 | 处理要求 |
|---|---|---|
| 高 | 可能影响 35 天预验收或 45 天正式验收 | 项目经理每日跟踪，明确责任人和解决时限 |
| 中 | 可能影响部分功能联调或交付质量 | 每周跟踪，纳入问题清单 |
| 低 | 对主链路影响较小，可通过文档或后续计划处理 | 记录并定期复核 |

## 3. 主要风险清单

| 风险编号 | 风险项 | 风险等级 | 影响 | 应对措施 |
|---|---|---|---|---|
| R-01 | 客户需求边界不清 | 高 | 可能导致开发范围扩大或验收口径变化 | 项目启动阶段确认网关侧范围，平台侧内容只作为边界说明 |
| R-02 | Dock3 协议字段理解偏差 | 高 | 可能导致平台与网关通信不兼容 | 建立字段矩阵，所有 topic、method、payload、reply 按 Dock3 口径校验 |
| R-03 | 飞控 SITL 行为与模拟回包不一致 | 高 | 可能影响真实任务、航点和飞控控制验收 | 区分 mock 验证和 SITL 实跑证据，关键动作补专项测试 |
| R-04 | 机巢模拟器联调不稳定 | 高 | 可能影响机巢控制、状态机和一键启航 | 提前完成机巢协议专项，保留日志和状态转换记录 |
| R-05 | MQTT 旧回包或旧进程干扰测试 | 中 | 可能导致测试结果误判 | 清理 Broker 环境，按 tid、method、topic 过滤，必要时启用严格验证 |
| R-06 | 文件 IO、数据库、上传任务阻塞主链路 | 高 | 可能影响实时遥测和指令响应 | 对耗时任务使用后台线程、异步任务或队列，进行非阻塞审计 |
| R-07 | 真实硬件缺失 | 中 | 真实 OTA、真实推流、真实负载能力无法完整验证 | 使用 adapter/mock，明确限制说明和后续硬件接入计划 |
| R-08 | 进度压缩导致测试不足 | 高 | 可能影响预验收和正式验收质量 | 设置阶段门禁，P0/P1 必须有脚本和日志证据 |
| R-09 | 跨模块接口变更频繁 | 中 | 可能导致联调返工 | 变更前同步接口文档，变更后执行回归测试 |
| R-10 | 验收材料不完整 | 中 | 可能影响正式验收效率 | 每个阶段同步归档脚本输出、日志、trace、问题闭环和说明文档 |

## 4. 风险应对策略

### 4.1 范围风险应对

- 项目范围限定在网关侧开发和联调。
- 平台前端、权限、工单、长期统计和媒体资源库不作为本项目交付项。
- 任何新增需求必须记录来源、影响范围和是否影响 45 天计划。

### 4.2 技术风险应对

- 对核心协议建立接口清单和字段清单。
- 对 P0/P1 功能建立专项测试脚本。
- 对无法接真实硬件的能力提供 mock、adapter、错误码和限制说明。
- 对高风险功能优先安排联调，不推迟到验收前处理。

### 4.3 进度风险应对

- 按阶段设置里程碑和阶段验收标准。
- 每日跟踪阻塞问题，每周复盘整体进度。
- P0 未稳定前不投入大量资源到 P2 深度优化。
- 预验收前完成全链路 E2E 和主要问题闭环。

### 4.4 质量风险应对

- 所有核心功能必须有脚本、日志或 trace 证据。
- 缺陷修复后必须执行回归测试。
- 关键 topic、method、错误码和状态机变化必须更新文档。
- 对断连重连、超时、非法参数和异常状态进行专项验证。

## 5. 风险跟踪机制

项目风险由项目经理统一维护，研发团队共同更新。风险跟踪内容包括：

- 风险描述。
- 风险等级。
- 当前状态。
- 责任岗位。
- 影响范围。
- 应对措施。
- 计划完成时间。
- 实际处理结果。

风险状态分为：新建、处理中、待验证、已关闭、延期处理。

## 6. 预验收前重点风险检查

第 35 天预验收前，需要重点确认以下事项：

1. P0 核心链路是否全部可重复验证。
2. P1 主业务流程是否形成闭环。
3. 机巢模拟器、飞控平台、网关、云端模拟器是否能够按顺序启动。
4. 关键问题是否均有处理结论。
5. 未完成项是否明确影响范围和整改计划。
6. 验收脚本、日志、trace 和说明文档是否齐备。

## 7. 正式验收前重点风险检查

第 45 天正式验收前，需要重点确认以下事项：

1. 预验收问题是否已整改或获得确认。
2. 全链路是否能够稳定复测。
3. 交付范围内功能是否均有证据。
4. 剩余限制是否均已形成说明。
5. 交付文档、配置、脚本和验收记录是否完成归档。
